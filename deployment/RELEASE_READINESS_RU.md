### Конкретное исправление после подтверждения

Сохранить работающий bare-vhost и его сертификат. Добавить/скорректировать
только www-vhost на порту 80 с сохранением ACME challenge, затем получить
доверенный **отдельный сертификат для www**, не заменяя действующую bare-lineage.
Использовать существующий ACME-клиент и способ продления. Если на VPS уже
используется Certbot webroot, после проверки реального webroot команда имеет вид:

```sh
certbot certonly --webroot --webroot-path ACTUAL_ACME_WEBROOT \
  --cert-name www-noir-atelier-ru -d www.noir-atelier.ru
```

`ACTUAL_ACME_WEBROOT` сейчас неизвестен; эта команда не запускалась. Если
действующий клиент/способ другой, сначала подготовить эквивалент под него,
не устанавливая второй ACME-клиент. После выдачи добавить HTTPS www-vhost,
который делает `301 https://noir-atelier.ru$request_uri`. Путь и query
сохраняются. Основной Node upstream менять ради www не требуется.
Фрагмент: `www-redirect.conf.example`; заполнить реальными проверенными путями,
не применять вслепую прежний общий шаблон. Перед каждым reload — `nginx -t`.

## Метрика: событие и момент подтверждения

| Событие | Когда вызывается | Что не считается подтверждением |
| --- | --- | --- |
| `add_to_cart` | После добавления выбранного размера/системы/цвета в локальную корзину | Просмотр карточки |
| `begin_checkout` | После входа в checkout с непустой корзиной, один раз на монтирование | Нажатие ссылки без входа |
| `order_created` | После успешного ответа сервера с сохранённым заказом | Нажатие кнопки, валидационная ошибка, пересчёт цены |
| `generate_lead` | После успешного сохранения заявки каждой из трёх форм | Нажатие кнопки или ошибка загрузки |
| `purchase` | Только серверная оплата **товара**, `paid`, не `mock`, есть paidAt, RUB/сумма совпадают с заказом, заказ не отменён | mock_paid, оплаченная доставка, completed без подтверждения оплаты, отменённый заказ |

Стоимость цели передаётся в `order_price` (исправлено по документации
[reachGoal](https://yandex.ru/support/metrica/ru/objects/reachgoal)); `value`
сохранён как пользовательский параметр. Имена/контакты/файлы/тексты заявок
в события не передаются. Сбой счётчика не мешает оформлению. Повторная покупка
того же заказа подавляется в localStorage текущего браузера; это не гарантия
дедупликации между разными устройствами.

**Реальная текущая логика:** `createOrder` создаёт оплату товара с `provider=mock`;
`mockPayOrder` ставит `mock_paid`. Единственный штатный переход в `paid` сейчас
подтверждает доставку, а не товар. Следовательно, в текущем процессе нет
достоверного основания посылать `purchase`; событие намеренно не сработает.
Подключение реальной оплаты/подтверждения товара — отдельная бизнес-задача,
которая не подменялась созданием заказа или статусом completed. Пользователь
может оценивать реальные заявки/сохранённые заказы отдельными целями.
Клиентское событие также требует посещения страницы заказа и не заменяет
серверный учёт или будущие offline-конверсии.

## Нужны ли четыре теста MinIO

Только первый тест `keeps material costs ... stores a private model` загружает,
читает и удаляет объект S3. Остальные три используют PostgreSQL и валидацию;
они теперь выполнены: **3 passed, 1 skipped**. Предыдущая формулировка,
что всем четырём нужен MinIO, была неточной.

Сравнение с исходной веткой: `storage.ts`, S3-команды, bucket-policy, endpoint,
credentials, upload/download-сервисы и схема/миграции не менялись. Чтение
публичного имени изображения уже хранится в mediaAssets и не выполняет операций S3.
Единственный общий слой — SEO-заголовки. Для него выполнен отдельный тест:
бинарный stream, Content-Type, Content-Disposition и Set-Cookie сохранены,
приватный ответ получает no-store/noindex. Поэтому MinIO-интеграция не является
обязательной проверкой этой правки и не имитировалась фальшивым S3-сервером.
Если при фактической выкладке понадобится менять storage location, bucket-policy,
endpoint или сервис загрузки — это выходит за текущий план: сначала поднять
изолированный MinIO и выполнить оставшийся интеграционный тест.

## Порядок публикации и отката для подтверждения

Локальная подготовка проверена: build/types/lint без ошибок (13 существующих
предупреждений lint), 35 тестов приложения, 16 интеграционных тестов PostgreSQL,
2 теста средства резервного копирования, 19 функциональных браузерных сценариев
и 5 дополнительных проверок SMART. Все 38 URL локальной sitemap возвращают
200 и правильный canonical; три отсутствующих URL — 404. Единственный
S3/MinIO-тест оставлен пропущенным по обоснованию выше. Production post-check
подготовлен и проверен синтаксически; успешная приёмка живого сайта ещё
не выполнялась и не заявляется.

1. Получить существующий SSH alias; только прочитать фактическую конфигурацию,
   текущий SHA/dirty-state, release-путь, manager/upstream и ACME-настройки.
   Если код на VPS новее, перенести SEO-коммиты поверх него без потери доработок.
   До выяснения путей и SHA переключение заблокировано.
2. Сохранить выбранные реальные nginx/env/manager-конфиги и их symlink-targets
   локально через `capture-config-backup.py`. Скрипт использует BatchMode и
   StrictHostKeyChecking=yes, не пишет на VPS, не печатает содержимое и
   сохраняет архив в игнорируемую `.local/config-backups` с доступом владельца.
   Проверяет состав tar и SHA-256. Нужны точные file-пути, каталоги/приватные
   ключи не принимаются. Старый release сохранить на сервере; не удалять
   сертификаты или прежнюю lineage. Зафиксировать путь текущего release/link
   и метаданные файлов для обратного переключения. Реальную резервную копию
   считать созданной только после успешного чтения и проверки архива.
3. После отдельного подтверждения публикации передать исходники в **новый**
   release, `npm ci`, build/types/tests/lint. Использовать действующее окружение,
   сверенные публичные `VITE_*` передать стадии сборки до `npm run build`,
   секреты БД/SMTP оставить в runtime EnvironmentFile, не в `VITE_*`.
   без seed, миграций, переустановки БД/MinIO и копирования локальных фикстур.
   Включить только найденный и сверенный ID Метрики; иначе оставить пустым.
4. Запустить новый release на свободном loopback-порту. Проверить sitemap,
   canonical/404, SMART-подписи, изображения, каталог/цену/корзину и формы.
   Полный тест заказа сначала на изолированной БД, без списаний и отправки СДЭК.
5. Применить узкий www-патч и отдельный сертификат описанным выше способом.
   Проверить реальное продление сертификата и `nginx -t`; выполнить reload.
6. Штатно переключить release/upstream, перезапустить только приложение,
   не перезагружать VPS. Сохранить прежний release готовым к возврату.
7. `node deployment/post-publish-check.mjs`: восемь URL/TLS/редиректов,
   sitemap, canonical, три настоящих 404, robots, SMART и ответы изображений.
   Затем браузер desktop/mobile, выбор варианта, цена, корзина и checkout.
   **Production-заказ не создаётся этим скриптом.** Одна тестовая запись заказа
   на production допустима только при явном включении её в подтверждение:
   согласованный тестовый аккаунт, пометка SEO TEST, без реальных оплат,
   писем/отправлений СДЭК, с блокировкой отправки аналитики. Иначе проверка
   на production заканчивается перед отправкой формы; полный тест — staging.
8. При неуспешной приёмке вернуть прежний release/upstream и штатно
   перезапустить приложение. Если откат нужен и для www — восстановить
   сохранённые nginx-файлы/ссылки по manifest, `nginx -t`, затем reload.
   Новый www-сертификат можно сохранить; старый bare-сертификат не трогался.
   Схема и данные БД не меняются, обратные SQL-операции не нужны. Старую
   source-ветку и рабочий release не удалять; историю Lovable не переписывать.

Выдача/продление сертификата — внешнее действие ACME, его нельзя «откатить»
удалением истории выдачи. Откат здесь означает возврат применяемой nginx-
конфигурации/lineage, при сохранении сертификатов и ключей в защищённом хранилище.
